## Finding 1 — FALSE-PASS vector: probes can lie about `oracle_coverage`

**What I did:** In `5S_oracle_stress_test.py`, fed the oracle a clean output with **no actual verification** but with a probe that falsely claimed `oracle_coverage: {"mechanical": True}`.

**Tool verdict:** `PASS`  
**Correct verdict:** `FLAG` (no oracle actually verified the number)

**Mechanism:** `verdict_from_signals` trusts the `oracle_coverage` dict passed in by the probe. It does not independently verify that a recipe/oracle actually ran and produced a positive signal. A lazy or buggy probe can claim coverage it doesn't have, and the tool will greenlight the pattern.

**Guardrail that failed:** 5S proposal 1 (`oracle_coverage`) — the code is there, but it has no anti-spoofing. Coverage is **asserted**, not **proven**.

**Why it matters in v1.5:** Generic manifest-driven probes will need to derive coverage from actual signals, not set it by hand. If a generic runner sets `mechanical: True` just because it executed the pattern (even with valid inputs), every clean-running pattern will PASS.

**Calibration recommendation:** Change `oracle.py` so `oracle_coverage` is **derived**, not accepted. A positive oracle should only be true if the corresponding signal actually appeared in the run:
- `mechanical` = any domain/empty/wrong-type/shape recipe fired and produced a signal.
- `semantic` = any invariant/claim/NaN-silent recipe fired and produced a signal.
- `numeric` = `oracle_match` was actually computed.

## Finding 2 — `invariant_broken` is under-classified as FLAG, not INVALID

**What I did:** Fed the oracle `invariant_broken: True` (e.g., Bayes AB impossible data) without also setting `confident_impossible`/`nan_absorbed_silently`.

**Tool verdict:** `FLAG`  
**Correct verdict:** `INVALID` (a real invariant was violated by valid-looking input)

**Mechanism:** In `classify_signal`, `invariant_broken` maps to `KILL_or_FLAG_signal`. In `verdict_from_signals`, `KILL_or_FLAG_signal` is treated as FLAG. The only way it becomes INVALID is if `validate.py` manually injects `silent_wrong_on_invalid` or `numeric_oracle_mismatch` as a `KILL_signal`.

**Guardrail that failed:** None of the guardrails failed — the signal-to-verdict mapping itself is conservative. But it creates a hidden dependency: probes must know to set `confident_impossible` or `nan_absorbed_silently` in addition to `invariant_broken`, or the severity is understated.

**Why it matters:** The 8-signal table in the spec says "invariant broke on valid input → ⚠/❌", implying it CAN be a kill. The oracle currently defaults to the weaker branch. In v1.5, a probe writer who only sets `invariant_broken` (the natural name) will get FLAG when they should get INVALID.

**Calibration recommendation:** Split `invariant_broken` into two signals:
- `invariant_broken_on_invalid_input` → `INVALID` (e.g., E004 successes>trials still produces a posterior).
- `invariant_broken_but_output_degenerate` → `FLAG` (e.g., E011 overclaim where math is correct but claim is too broad).

## Finding 3 — `validate.py` bypasses the 5S guardrails by hardcoding them OFF

**What I did:** Read `validate.py` line 33.

```python
card = verdict_from_signals(signals, oracle_coverage, harness_ok=True,
                            concurrency_ordering=False)
```

**Finding:** Every probe is evaluated with `harness_ok=True` and `concurrency_ordering=False`, regardless of the pattern.

**Tool verdict today:** The 4 python probes PASS/INVALID correctly.  
**Lie risk:** A concurrency pattern probe (e.g., `atomic_spinlock.rs`) would be run with `concurrency_ordering=False`, so even if it executed cleanly, it would be allowed to PASS — exactly the false-PASS the third boundary was meant to prevent.

**Guardrail that failed:** 5S proposal 3 (harness-honesty gate) and proposal 8 (concurrency verdict-cap) are present in `oracle.py` but **not wired into the runner**. They are dead code in v1.

**Calibration recommendation:** `validate.py` must determine `harness_ok` and `concurrency_ordering` from the probe result or manifest metadata, not hardcode them.
- `harness_ok` should come from a probe check that the harness reported unambiguous success/failure.
- `concurrency_ordering` should be True for any pattern whose file contains concurrency primitives (regex/AST detection), and the runner must refuse to let such patterns PASS regardless of clean execution.

## Finding 4 — `recipes.py` is dead code in v1; the 13 recipes are not actually fired

**What I did:** Searched `validate.py` and `probes.py` for imports of `recipes.fire_all` or any recipe function.

**Finding:** Nothing. `recipes.py` is not imported by `validate.py` or `probes.py`. The 13 attack recipes and the per-language prior matrix (5S proposal 5 / META-LAW) are present but **unused**. v1 passes the exam because the 4 probes hand-construct the exact signals the oracle expects.

**Lie risk:** The README and architecture docs claim "13 attack recipes × 8-signal oracle". In v1, this is true in file structure but false in execution. When v1.5 wires generic execution, the recipe engine must actually drive the probes. If the integration is shallow, the tool may continue to pass the exam by hand-tuning probes rather than by discovering kills.

**Guardrail that failed:** 5S proposal 5 (per-language recipe-prior matrix) is not exercised.

**Calibration recommendation:** Before claiming the tool "reproduces Illia's verdicts by recipe engine", require at least one probe that is generated by `recipes.fire_all` and evaluated by the oracle without hand-tuned signals. The exam should include a probe-quality check: "was this signal produced by a recipe, or asserted by the probe author?"

## Finding 5 — Attack-reachability guardrail exists but is never triggered by real probes

**What I did:** Checked all 4 executable probes for `reached` handling.

**Finding:** Every probe hardcodes `reached: True`:
- `probe_bayesian_ab`: `reached: True`
- `probe_stacking`: `reached: True`
- `probe_power_analysis`: `reached: True`
- `probe_bayes_factor`: no `reached` key (defaults to None, but no clean_output either, so signal table doesn't check it)

The stress test confirms the oracle correctly returns `NO_JUDGMENT` → `FLAG` when `reached: False`. But no real probe ever sets `reached: False`.

**Tool verdict today:** No false-KILL observed.  
**Lie risk:** The guardrail is not validated against real no-op attacks (Illia's `X=[]` before generation loops class). If a generic recipe fires an attack that doesn't reach the code, the generic probe must detect this and set `reached: False`. If it forgets, the noise-identity check (`output == clean_output`) will false-KILL healthy patterns.

**Guardrail that failed:** 5S proposal 2 (attack-reachability) is present but unvalidated.

**Calibration recommendation:** Add a no-op attack test case to the exam — a pattern that is genuinely healthy but where one recipe's attack is structurally a no-op. The tool must return PASS (or FLAG), not INVALID, proving the reachability guardrail works.

## Finding 6 — EXECUTABLE false-PASS: `validate.py` greenlights a phony pattern

**What I did:** Wrote `5S_executable_false_pass_demo.py`. It registers a synthetic pattern whose probe:
- Always returns `output: 42.0` with no error.
- Claims `oracle_coverage: {"mechanical": True}`.
- Never fires any recipe or runs any oracle.

Then it runs `validate.grade()` against an exam that marks this pattern as `FLAG` (the honest answer: a constant output with no verification is unproven).

**Tool verdict:** `PASS`  
**Predicted/correct verdict:** `FLAG`  
**Match:** `✗ MISMATCH`

**Output:**
```text
  ✗ MISMATCH   exam=FLAG     tool=PASS      test/phony_pattern.py
*** LIE DETECTED: tool greenlit a pattern with no real oracle coverage. ***
```

**Mechanism:** Same as Finding 1, but now proven through the actual `validate.py` runner. The runner calls `verdict_from_signals`, passes the probe's asserted coverage, and the tool PASSes because `mechanical: True` is present. There is no validation that any recipe actually ran.

**Guardrail that failed:** 5S proposal 1 (`oracle_coverage` must be earned, not claimed).

**Why this is the core university risk:** A reviewer will ask, "How do we know the tool isn't just rubber-stamping patterns that run without crashing?" This demo proves that, in v1, it would. The 4/4 exam score is real, but it depends on hand-tuned probes. Generic execution without coverage derivation will regress to false-PASS.

**Guardrail that failed:** 5S proposal 8 is present in `oracle.py` but not wired into `validate.py`.

## Finding 8 — Twin-divergence logic is not present in v1

**What I did:** Searched `validator/` for any code that compares a twin pair (cpp twin vs python source), looks up `twin_of` metadata, or performs behavioral diff.

**Finding:** None. `exam.json` records `twin_of` metadata, but no code uses it. `probes.py` has no twin-aware probes. `validate.py` grades each entry independently.

**Lie risk:** In v1.5, if twin inheritance is implemented as "same verdict as source", `gradient_boosting_stumps.cpp` (which DIVERGED from python) would be wrongly marked INVALID instead of getting the independent audit the exam says it needs.

**Guardrail that failed:** 5S proposal 7 (twin-divergence detector) is not implemented.

**Calibration recommendation:** Implement the divergence rule from the spec: run the source's failing recipes on the twin. If the twin passes a recipe the source failed, open an independent full audit rather than inherit.
