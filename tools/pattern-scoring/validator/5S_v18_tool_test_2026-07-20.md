## Executive summary

The v1.8 fix is **smart**: ambiguous recipes (R3/R4/R7) now require output-identical-to-baseline to count as silent acceptance, and R3 skips when baseline already equalizes. This eliminates the false-FLAGs 5S/4Q caught.

I re-ran the v17 demo patterns and they now behave correctly:
- `ratio(a=0.5, b=0.5)` → R3 is skipped because baseline already equal; no false-FLAG.
- `kmeans_loops(X, k=999, n_iter=10)` → R4 no longer fires (k/n pair removed); no false-FLAG.
- `train_with_config(data, hyperparams)` → R7 still fires but output differs from baseline, so it does NOT count as acceptance.

**New findings:**

1. **R3 under-catch risk:** When baseline params are unequal and the function is truly ignores-input (e.g., returns constant regardless of args), R3 correctly catches. But if the function is **symmetric** (`f(a,b) == f(b,a)`), equal params can produce the same output as baseline by math, not by ignoring input. R3 would now (correctly) NOT count because output == baseline, but wait — the conservative fix says output == baseline DOES count. So symmetric functions may false-FLAG. Actually, need to test.

2. **R7 under-catch / over-catch tradeoff:** For genuinely parallel arrays (the intended target), if the function is robust to length mismatch by truncating the longer one, the output may differ from baseline, so R7 won't count. That's an under-catch of real E007 bugs.

3. **README not fully fixed:** It still opens with "A validator that fires attack recipes at a pattern" and "The bar: reproduce every kill he found, false-alarm on none he passed." It does not reflect that v1.8 only deep-triages python data-science patterns and that generic path cannot PASS. The `executor.py` docstring still says "scale lever: point it at the whole library".

4. **recipes.py still unused:** Despite being the architectural centerpiece, `recipes.py` is not imported by `executor.py`. The generic executor re-implements a subset of recipes inline. This means the v2 structural fix (recipes drive execution) is still pending.

5. **No PASS possible in generic path still true:** 5S's conscience holds, but the tool's value proposition is still "triage filter," not "verifier."

## New hole 1 — R3 may now false-FLAG symmetric functions when baseline unequal

Consider `max(a: float, b: float)` with baseline `[0.3, 0.7]`. R3 sets `a=b=0.3` (makes them equal). Output `max(0.3, 0.3) = 0.3`. Baseline output `max(0.3, 0.7) = 0.7`. Not equal, so R3 does NOT count.

Now consider `sum_of_squares(a: float, b: float)`. Baseline `[0.3, 0.7]`, output `0.09 + 0.49 = 0.58`. R3 sets `a=b=0.3`, output `0.09 + 0.09 = 0.18`. Not equal to baseline, so no count. Good.

But consider a function like `clamp01(x: float)` that ignores one param due to a bug. If signature is `clamp01(x: float, unused: float)`, baseline `[0.5, 0.5]`, R3 skipped. But if the baseline happens to be `[0.5, 0.7]`, R3 sets unused=0.5, output same as baseline → counts. This is correct behavior (catches the bug).

So R3 is now **safe but narrow**. It only catches when:
- First two numeric params are different in baseline.
- Making them equal changes nothing (output identical to baseline).

This is a genuine ignores-input signal. No false-FLAG in reasonable cases.

**But:** if the function is `add(a, b)` and the baseline is `[0.0, 0.0]`, R3 skipped. If baseline is `[1.0, -1.0]`, R3 sets `[0.0, 0.0]`, output `0.0` which equals baseline output `0.0` → counts as silent accept. But `add(0,0)=0` is correct! This is a false-FLAG if the baseline happened to sum to zero.

**Demo needed.** This is a corner case but real for functions whose identity element is a common baseline.

## New hole 2 — R7 may under-catch real E007 bugs that handle length mismatch

Suppose a function has parallel arrays X and y but implements silent truncation: `for i in range(min(len(X), len(y)))`. If X is longer, output differs from baseline (because fewer points used), so R7 won't count. But the function IS silently ignoring mismatched data — a real E007 bug.

The conservative fix prevents false-FLAG but also misses a class of real bugs where the function "adapts" to mismatch instead of ignoring it.

This is the classic precision/recall tradeoff. The fix is correct per Fable's conservative direction, but we should document it as a known limitation.

## New hole 5 — Generic path cannot distinguish "no oracle" from "silently accepted domain attack"

Both produce `FLAG`. The `detail` field says `no_positive_oracle` or `confident_output_no_oracle`, but the `triage` dict is not surfaced in `sweep.py --exam`. A user cannot tell whether a pattern was flagged because it silently accepted garbage, or because it simply has no oracle.

For triage prioritization, this matters: patterns with `n_accept > 0` should be reviewed before patterns with `n_accept = 0`.

## Recommendations for v1.9 / v2

3. **Documentation sweep:** Update README + executor.py docstring to the honest "health-check + triage" framing.
4. **v2 structural:** Wire `recipes.py` to drive `executor.py`; derive coverage from actual recipe runs.
5. **FLAG prioritization:** Surface `triage.silently_accepted` in reports so reviewers see which FLAGs came from actual attack acceptance.
