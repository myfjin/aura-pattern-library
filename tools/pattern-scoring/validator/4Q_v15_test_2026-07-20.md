# 4Q — validation tool v1.5 adversarial test report
**2026-07-20**

## Baseline

`full_sweep.py` ran in 582s over 1,399 patterns: 1,399/1,399 BASELINE-OK health; 328 python data-science patterns FLAGged; 49 SKIP; 0 INVALID in the whole-library sweep.

Fable correctly identified the honest limitation: the generic executor uses blunt attacks (-1e9, None, NaN) and found 0 silent-acceptance INVALIDs at scale. I attacked whether the tool is honest about that limitation and whether it still has lie paths.

## Finding 1 — false-SKIP at scale: `bayes_factor_normal_means.py` should be INVALID but is SKIP

**Pattern:** `python/data-science/bayesian_iii_approximate_inference/bayes_factor_normal_means.py`
**Hand probe status:** `probes.py` contains `probe_bayes_factor()` with a numeric oracle that correctly detects wrong-math (code=1.24 vs true≈2.96e24) and emits INVALID.
**`sweep.py --exam` verdict:** `INVALID ✓` (uses `judge()` which calls hand probes).
**`full_sweep.py` verdict:** `BASELINE-OK + SKIP` (uses `executor.evaluate()` directly, ignoring hand probes).

**4Q predicted:** `full_sweep` should also report INVALID because the probe exists and is proven.
**Tool verdict:** SKIP.
**Disagree.**

**Mechanism failure:** `full_sweep.py` does not use `sweep.judge()`'s hybrid oracle-probe / generic-triage logic. It calls `evaluate()` directly, so any pattern that the generic executor cannot build a baseline for (e.g., because the entry function has complex annotations) gets SKIP, even if a hand probe with a numeric oracle exists.

**Guardrail failed:** 5S's oracle_coverage floor at scale. The scale runner bypasses the strongest oracles.

**Suggested fix:** `full_sweep.py` should use the same `judge()` hybrid as `sweep.py`. Definitive probes must run before or alongside generic triage.

## Finding 2 — domain-aware attacks are missing; hand-audit bugs remain invisible at scale

**Pattern:** `python/data-science/statistical_modeling/power_analysis_sample_size.py`
**Executor attack values for `p1` (probability):** `R1_domain_under = -1e9`, `R6_wrong_type = None`, `R6_wrong_type = "сорок два"`.
**What the hand audit found:** `p1=1.5` (probability > 1) is silently accepted by `sample_size_two_proportion`, returning `1` with no error. Same for `p1=-1.0`, `p1=2.0`, `p1=-1e9`.
**What the executor detects:** `-1e9` does NOT raise in `sample_size_two_proportion` either; the executor's reported `reject=10` comes from other functions (e.g., `two_proportion_power` raises on `p1=-1e9`) and from wrong-type attacks. The executor never tests `p1=1.5` or `p1=-1.0` because its attacks are not domain-aware.

**4Q predicted:** The generic executor cannot reproduce the hand-audit E003 finding.
**Tool behavior:** It does not reproduce it; it only sees a generic FLAG.
**Mechanism failure:** `attack_fixtures()` is not domain-aware. It does not read param names like `p1`, `alpha`, `rate`, `u` to choose semantically meaningful attacks (probability→1.5, rate→-1, alpha→-0.05, u→1.5). It uses one blunt numeric underflow.

**Suggested fix:** Add a domain-aware recipe layer that maps common parameter names to semantically invalid values (probability out of [0,1], negative rate/alpha, u≥1, etc.). This is exactly the E001–E009 catalog turned executable.

## Finding 3 — cross-param impossible (E004) and degenerate-equal (E002/E003) recipes are not implemented in `attack_fixtures`

**Observation:** `executor.attack_fixtures()` only implements R1, R5, R6, R8, R9. It does NOT implement R2 (domain-over), R3 (degenerate-equal), R4 (cross-param impossible), R7 (shape mismatch), R10 (numeric oracle), R11 (invariant stress), R12 (mutation), R13 (state sequence).

**Example:** `sample_size_two_proportion(p1, p2, alpha, target_power)` has two probability params. A domain-aware R2 would test `p1=1.5`. R3 would test `p1==p2` (zero effect). R4 would test `successes>trials` if applicable. None are fired.

**4Q predicted:** The generic executor is recipe-incomplete, not just domain-blind.
**Tool behavior:** Confirmed.

**Suggested fix:** `executor.py` must consume `recipes.ALL_RECIPES` (or a generic mapping of them) rather than a hand-rolled subset. The recipe library already implements R1–R13; the executor does not use it.

## Finding 4 — third boundary not applied in generic executor

**Observation:** `executor.evaluate()` does not detect concurrency primitives or cap python concurrency patterns at FLAG. It hardcodes `concurrency_ordering=False` in its call to `verdict_from_signals`. The static scan from `validate.py` is not reused.

**4Q predicted:** A python concurrency pattern (if any existed in the DS sphere) could run single-threaded, produce a finite number, and be FLAG/PASS without the tool admitting ordering is un-runnable.
**Tool behavior:** Confirmed gap.

**Suggested fix:** Add `_scan_concurrency()` or similar to `executor.py` and pass the result to the oracle. Patterns with concurrency primitives get `concurrency_ordering=True` regardless of runtime result.

## Finding 5 — health sweep is honest but shallow

**Observation:** All 1,399 patterns are BASELINE-OK. The tool runs each pattern's own self-test and reports exit code. It does not judge the self-test's strength.

**Risk:** A pattern with a self-test that always passes trivially (e.g., only prints, no real asserts) will be BASELINE-OK. I searched python files for 0 asserts or tautological asserts and found none in the current sweep set, but this was a shallow check.

**4Q assessment:** The health sweep is honest about what it measures ("does the self-test run clean?"), but the report should label it as "self-test health" not "pattern correctness." A user could misread 1,399/1,399 BASELINE-OK as "all patterns are fine," which is not what the tool claims but is easy to misread.

**Suggested fix:** Report should separate:
- `HEALTH` = self-test ran clean (mechanical sanity)
- `TRIAGE` = deep attack result (only for python DS)
- `VERDICT` = only after oracle/human review

## Finding 6 — severity downgrade at scale

**Observation:** Generic `silent_domain_acceptance` is a `FLAG_signal`, not a `KILL_signal`. So even when the generic executor finds a silent acceptance, it emits FLAG, not INVALID. Hand probes emit INVALID for the same class.

**Example:** `power_analysis_sample_size.py` is `FLAG` from the generic executor. In the fixed hand-probe path, the tool also FLAGs it (after round-2 calibration). So they agree on FLAG here. But for `bayesian_ab_beta.py`, the hand probe says INVALID; the generic executor says FLAG.

**4Q assessment:** This is a deliberate conservative choice and is honest. But it means the tool's whole-library output is mostly FLAGS, not actionable INVALIDs. The user must still review 328 patterns. The tool's claim of "machine speed" is true for triage, not for final verdicts.

## Summary: where v1.5 still lies or under-reports

| Issue | Severity | Honest? | Fix |
|---|---|---|---|
| full_sweep ignores hand probes → bayes_factor SKIP | High | Under-reports | Use `judge()` hybrid |
| Domain-unaware attacks miss hand-audit bugs | High | Incomplete | Map E001–E009 to param-name values |
| executor uses only 5/13 recipes | High | Incomplete | Wire all recipes |
| Concurrency cap missing in generic executor | Medium | Over-claims safety | Add static scan |
| Health sweep could pass trivial self-tests | Low | Honest but shallow | Label report sections clearly |
| Generic silent-acceptance = FLAG not INVALID | Low | Conservative | Keep; document as triage |

## Proposals for v1.6

1. **Hybrid scaling:** `full_sweep.py` uses `sweep.judge()` so proven oracle probes run before generic triage.
2. **Domain-aware recipe values:** param-name-driven attack values from the E-catalog (probability, rate, alpha, u, n, k, etc.).
3. **Full recipe wiring:** `executor.attack_fixtures()` should delegate to `recipes.fire_all()` with a generic arg_spec builder.
4. **Concurrency scan in executor:** apply the third boundary to all python patterns, not just hand probes.
5. **Self-test strength metric:** count asserts and report it; flag patterns with zero or trivial asserts as `HEALTH-WEAK`.
