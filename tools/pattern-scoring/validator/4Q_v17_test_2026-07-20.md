## New findings in v1.7

### N1 — R3 still false-FLAGs symmetric baselines

**Synthetic test:** `def mean(a: float, b: float) -> float: return (a + b) / 2.0`
**Tool verdict:** `FLAG [accept=3 reject=4]`
**Reasoning:** `_valid_for` returns `0.5` for both `a` and `b`, so the baseline already has equal params. R3 constructs a mutated args list that is identical to the baseline. The output is therefore identical to baseline, and the constrained R3 counts it as "ignores input."

This is a false-FLAG because equality of inputs is valid for `mean`. The constraint catches output-identity, but the mutation is degenerate when the baseline already equalizes.

**Suggested fix:** R3 should only count when the mutated value is *different* from both baseline params. If baseline has equal params, skip R3 or force a value that differs (e.g., set both to `baseline[0] + 1.0` and compare to output at that new value).

### N2 — R4 false-FLAGs legitimate clamp/clip functions

**Synthetic test:** `def clip_count(count: int, limit: int) -> int: return min(count, limit)`
**Tool verdict:** `FLAG [accept=6 reject=4]`
**Reasoning:** R4 sets `count=999, limit=10`. The function correctly returns `10`. The tool counts this as silent acceptance of "cross-param impossible" because count > limit. But `min`/`max`/`clip` functions are *designed* to handle count > limit.

This is a false-FLAG. R4 assumes part > whole is always invalid, which is true for physical containment (successes > trials) but not for clamping.

**Suggested fix:** R4 should not fire when the function name or param names suggest a clamp/limit operation (`clip`, `clamp`, `min`, `max`, `bound`, `limit`, `cap`). Or the acceptance signal should be weaker and only FLAG if the function does not mention/min/max in its source.

### N3 — R7 false-FLAGs non-parallel list functions

**Synthetic test:** `def concat_lists(a: list, b: list) -> list: return a + b`
**Tool verdict:** `FLAG [accept=2 reject=2]`
**Reasoning:** R7 makes `a` one element longer and `b` one element shorter. `concat_lists` still returns a list. The output is finite/full, so it counts as silent acceptance of shape mismatch. But `a` and `b` are not parallel arrays.

**Suggested fix:** R7 should only fire when param names suggest parallel arrays (`X`, `y`, `labels`, `values`, `features`, `target`, `events`, `times`). A function with two arbitrary lists is not a shape-mismatch candidate.

### N4 — numeric oracle spoof still possible with new-style metadata

**Observation:** `oracle.derive_coverage()` now requires `oracle_run=True`, `oracle_truth` not None, and `oracle_match` not None. An old-style `oracle_match=True` no longer produces PASS.

**New-style spoof:** Set `oracle_run=True`, `oracle_truth=42.0`, `oracle_match=True`. Result: PASS.

**Assessment:** This is a reduced but still real trust boundary. A probe author can still fabricate a ground truth and claim the oracle matched it. However, the lie now requires constructing a plausible truth value, not just a boolean.

**Suggested fix:** The numeric oracle should be a separate, auditable module that computes ground truth from the same fixture and returns `oracle_match`. Probes should not report it as metadata.

### N5 — sweep.py / validate.py still use old probe booleans

**Observation:** `sweep.py` and `validate.py` still append `("silent_wrong_on_invalid", "KILL_signal")` based on `r.get("confident_impossible")` or `r.get("nan_absorbed_silently")`. These booleans are probe-asserted, not derived from raw outputs.

**Risk:** A hand probe can still inject a KILL verdict by setting these flags. This is acceptable for v1 because hand probes are curated, but it is not the fully-derived oracle model promised by v1.5+.

**Suggested fix:** Move the semantic KILL detection into a generic oracle that compares poisoned vs clean outputs. Hand probes should only collect raw outputs.

### N6 — full_sweep.py still has a no-op progress print

Line 43-45 contains an empty string concatenation (`" ".join(... for ... in [][:0])`) that evaluates to `""`. This is harmless but sloppy.

## Summary

v1.7 fixes the major v1.6 gaps (R4, R7, name-aware baseline builder, honesty language). But the new recipes introduce new false-FLAG paths:
- R3 still fires when baseline already equalizes params.
- R4 falsely flags clamp/clip functions.
- R7 falsely flags non-parallel list functions.

The numeric oracle spoof is harder but still possible. The hand-probe semantic booleans remain a trust boundary.

## Proposals for v1.8

1. **R3 mutation must differ from baseline.** If baseline params are already equal, either skip R3 or mutate to a new distinct value and compare against that new baseline.
2. **R4 exclude clamp families.** Do not fire on functions/names containing `clip`, `clamp`, `min`, `max`, `limit`, `cap`, `bound`.
3. **R7 require parallel-array naming.** Only fire when param names suggest alignment (`X/y`, `features/labels`, `times/events`, `predicted/actual`, etc.).
4. **Numeric oracle as module.** Separate ground-truth computation from probe metadata.
5. **Generic semantic oracle.** Replace `confident_impossible` / `nan_absorbed_silently` probe booleans with output comparison.
6. **Clean no-op progress print.** Remove the empty concatenation in `full_sweep.py`.
