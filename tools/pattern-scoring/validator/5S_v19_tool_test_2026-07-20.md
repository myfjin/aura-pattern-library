## 2. R3 trivial-output guard

### v1.9 code under test

`executor.py` line 242-246:

```python
elif recipe in ("R3_degenerate_equal", "R4_cross_param_impossible", "R7_shape_mismatch") \
        and not r["raised"] and out is not None and out == base_result.get("output") \
        and _finite_or_full(out) and out not in (0, 0.0, -0.0):
    # 5S v18: exclude TRIVIAL outputs (0/empty) — a symmetric fn like add(1,-1)==add(0,0)==0
    # matches by coincidence, not by ignoring input. Require a distinctive matched output.
    n_accept += 1
```

The guard excludes scalar `0` variants. `_finite_or_full` already requires collections to be non-empty, so the "empty" part of the comment is handled implicitly.

### Test A — coincidental zero (the fix target)

```python
def product(a: float = 0.0, b: float = 5.0) -> float:
    return a * b
```

- Baseline `(0.0, 5.0)` → output `0.0`.
- R3 equalizes `b` to `a` → `(0.0, 0.0)` → output `0.0`.
- `out == baseline_out == 0.0`, so R3 is **excluded by the trivial-output guard**.
- Result: `accept=2`, but both accepts come from **R1_domain_under** (`-1e9` attacks), not R3.

**Verdict:** the trivial-output guard defeats the coincidental-zero R3 false-FLAG.

### Test B — bounded / clamp function (the remaining edge)

```python
def clip_value(x: float = 0.5, lower: float = 0.0, upper: float = 1.0) -> float:
    return max(lower, min(x, upper))
```

- Baseline `(0.5, 0.0, 1.0)` → output `0.5`.
- R3 equalizes `x` and `lower` → `(0.5, 0.5, 1.0)` → output still `0.5` (mathematically valid, not ignored input).
- `out == baseline_out == 0.5`, which is **not in `(0, 0.0, -0.0)`**, so R3 **is counted**.
- Result: `FLAG [accept=4 reject=6]`.

Per-recipe counts for `clip_value`:

| Recipe | idx | baseline_out | mutated_out | counted? |
|---|---|---|---|---|
| R1_domain_under | 0 | 0.5 | 0.0 | ✅ |
| R1_domain_under | 1 | 0.5 | 0.5 | ✅ |
| R1_domain_under | 2 | 0.5 | 0.0 | ✅ |
| R3_degenerate_equal | 0 | 0.5 | 0.5 | ✅ |

The R1 counts are also false-FLAGs for a bounded function: feeding `-1e9` into `lower` or `upper` is a legal input to a clipper, and the finite output is expected. Both R1 and R3 conspire here.

### Test C — identity/threshold function

```python
def soft_threshold(x: float = 1.0, threshold: float = 1.0) -> float:
    return max(0.0, x - threshold) if x > threshold else 0.0
```

- Baseline `(1.0, 1.0)` → output `0.0`.
- R1/R2 domain attacks produce finite outputs that are counted.
- R3 is not applicable because baseline `x == threshold` already equalizes the two numeric params.
- Result: `FLAG [accept=3 reject=4]`.

This one is harder to call a false-FLAG because R2 attacks `threshold` with `1.5` and gets `2.0` — a finite output that looks like silent acceptance. A human knows `threshold=1.5` is not semantically invalid, but the tool has no oracle to know that. So Test C is more honest-triage than false-FLAG.

### v2 (bounded-function structural fix)
The bounded-function problem is not a guard tweak; it is the absence of semantic knowledge:
- R1/R3 treat any finite output on an extreme/identity mutation as "silent acceptance".
- Bounded functions are *designed* to produce finite outputs on extreme inputs.
- The durable fix is recipe metadata (e.g., `kind="bounded"` or `ambiguity=high`) plus per-pattern oracles that can PASS legitimate behavior. That's the v2 work already named (`recipes.py` driving execution, per-pattern oracles).

### Do not chase this with another local heuristic
Tightening R3 further (e.g., excluding outputs equal to any baseline param) would start under-catching real ignores-input bugs. The bounded-function edge is the conservative-triage tradeoff. It is better to honestly FLAG a clipper for human review than to silently let an ignores-input bug pass.
