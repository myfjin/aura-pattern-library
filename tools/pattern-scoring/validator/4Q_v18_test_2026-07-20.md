## New findings in v1.8

### N1 — `full_sweep.py` module docstring still overclaims

**Line 3:** `"full_sweep.py — validate the WHOLE library (all 5 languages, ~1399 patterns)."`
**Runtime print:** `"HEALTH-CHECK + DS-TRIAGE (not full verification)"` — correct.
**Discrepancy:** The module docstring and README still use the word "validator" and "verdict" without distinguishing oracle-probe verdicts from generic triage.

**Suggested fix:** Update the `full_sweep.py` docstring to match the runtime honesty language. README should add a paragraph distinguishing:
- `validate.py` / `sweep.py --exam`: oracle-backed verdicts against Illia's hand-verdicts
- `full_sweep.py`: health check + conservative triage (not final verdicts)

### N2 — progress print still contains no-op concatenation

**Line 43-45:** `" ".join(f"{k}:{sum(v.values())}" for k, v in [("done", by_lang_health)][:0])` always evaluates to `""`.

**Suggested fix:** Remove the empty join, as done in v1.6 but apparently reverted.

### N3 — generic executor still hardcodes `reached=True`

All attack fixtures in `evaluate()` set `r["reached"] = True` unconditionally. The attack-reachability guardrail from round-2 is not applied in the generic path. While this does not cause false-KILLs because `clean_output` is not passed, it means the tool does not detect no-op attacks in the generic path. This is an honest limitation but should be documented.

### N4 — strict functions that reject all attacks are still FLAGged, not PASSED

**Synthetic:** `strict_prob(p)` raises ValueError for p outside [0,1].
**Tool verdict:** `FLAG [accept=0 reject=3]` reason `no_positive_oracle`.
**Assessment:** This is correct per the tool's contract (PASS requires positive oracle), but a human may expect rejection of all attacks to be a PASS. The report language is accurate: FLAG = "no positive oracle."

### N5 — POSITIVE_STEMS 0-attack can false-FLAG legitimate functions

Functions with params like `timeout`, `epsilon`, `rate` that legitimately accept 0 will be flagged. This is conservative and honest, but contributes to the large FLAG count. Without a description oracle, the tool cannot know whether 0 is valid.

### N6 — R4 only handles success/trial/count/total/hit/total

Other part-whole pairs like `successes`/`n`, `observed`/`expected`, `k`/`total` are not covered. This is a coverage gap, not a false-FLAG.

## Summary

v1.8 successfully fixes the R3/R4/R7 over-broad false-FLAGs without under-catching real ignores-input bugs. The conservative rule (only count output-identical-to-baseline for ambiguous recipes) is sound.

Remaining honesty issues are minor:
- Module docstring overclaim

The tool is now sharp: it does not false-condemn valid handling, and it still catches unambiguous domain violations and ignores-input patterns.
