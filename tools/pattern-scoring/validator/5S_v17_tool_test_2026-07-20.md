## New holes

### Hole 1 — R3 still false-FLAGs when baseline already has equal first two numerics

**Synthetic demo:** function `ratio(a: float, b: float) -> float` with default baseline `a=5, b=5`.

R3 sets `a=5, b=5` (same as baseline). Output is `1.0`, same as baseline output. Tool counts as `n_accept` and FLAGs.

But `a=b=5` is valid input producing correct output. This is a false-FLAG.

**Fix recommendation:** R3 should compare against a **different baseline** where the two params are NOT equal, then check if setting them equal changes the output appropriately. Or only count R3 as a signal if the equal-params output equals the baseline AND the baseline had unequal params.

### Hole 2 — R4 `("k", "n")` fallback can false-FLAG unrelated k/n params

**Example:** function `kmeans(X: list, k: int, n_iter: int)`. `k` is clusters, `n_iter` is iterations. Setting `n_iter=10, k=999` is not "k > n impossible"; it's just "run 999 clusters for 10 iterations." If the function returns a finite result, R4 counts it as silent acceptance of impossible relation.

**Fix recommendation:** Remove the generic `("k", "n")` fallback, or only apply it when both params are clearly count-pair semantics (e.g., param docstrings / names both suggest part-whole relationship).

### Hole 3 — R7 false-FLAG when two list params are not parallel

**Example:** function `train(X: list, hyperparams: list)`. X is data, hyperparams is a list of settings. Making them unequal length is not a shape mismatch; they're unrelated. If the function handles it, R7 counts as silent acceptance.

**Fix recommendation:** R7 should only fire when param names suggest alignment (e.g., `X` and `y`, `data` and `labels`, `times` and `events`). Generic "first two flat lists" is too broad.

### Hole 4 — `full_sweep.py` only triages python DS patterns, not sysadmin

`full_sweep.py` line 33:
```python
if lang == "python" and "/data-science/" in f and h["health"] == "BASELINE-OK":
```

This means `token_bucket_limiter.py` and `ttl_cache.py` (in `system-administration/`) get only `polyglot.selftest` health. Their bugs are not triaged by the generic executor.

This is **an honest scope boundary** but it is not clearly documented. The README says "validate the WHOLE library" but the code only deep-triages DS python patterns.

**Fix recommendation:** Either extend deep triage to sysadmin python patterns (with I/O-safe probes), or explicitly document the scope as "python data-science deep triage + all-language health check."

### Hole 6 — Generic bayes_factor no longer SKIP but still not INVALID without hand-probe

`executor.evaluate` on `bayes_factor_normal_means.py` now returns `FLAG` instead of `SKIP` (because name-aware baseline builder can construct args). But it does not return `INVALID` because generic path has no numeric oracle.

A user might see "no SKIP" and think the wrong-math was examined. It was run, but not verified.

This is the **"examined vs verified" distinction** — 5S's core thesis. The tool should report `FLAG-no_oracle` not as "we looked at it" but as "we could not verify."
