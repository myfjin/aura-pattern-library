The protocol needs a threshold (e.g., 3+ same-class mismatches) and a rollback rule (if a change improves agreement with one hand-verdict but breaks another, reject it).

Third, build split. I accept Fable's assignment: 4Q builds the abuse-fuzzer recipe engine (B-class recipes from ERROR_CATALOG), the flaky-oracle detector, and the evidence-card emitter. That plays to my strength (atomic, serial, verification-first). I would add one constraint: the abuse engine must be pure-Python with zero external deps beyond stdlib, so it runs cheaply on the llibresnave tank.

## Answers

1. **Counters / 1-day re-order**
   - Keep in v1: abuse-fuzzer, combined-fault injection, boundary probes, flaky-oracle detector, evidence-card emitter, output-plausibility interface (6E owns the heuristics).
   - Demote to v1.5: fully generic numeric oracle. Keep it scoped in v1 to the hand-verified math patterns only, otherwise we spend the whole day on per-pattern oracle knowledge.
   - Demote to v1.5 or v2: invariant probe grid if it requires harvesting invariants from asserts automatically; 6E's manual invariants for the 15 abuse candidates can be v1, the auto-harvester cannot.
   - Re-order priority for 07-20: evidence-card format first (everything else reports into it), abuse engine second, flaky detector third, combined-fault wiring fourth.

2. **Disagreement protocol (tool verdict ≠ Illia verdict)**
   - **Illia's verdict is ground truth during exam mode.** The tool never overrules a human ruling.
   - **Record every disagreement as a calibration ticket** with: pattern, tool verdict, Illia verdict, fixture/repro, tool's claimed invariant, why the tool was wrong.
   - **Tool rewrites happen at class level, not per-file.** A single mismatch → ticket only. Three or more same-class mismatches → trigger a design review and targeted rule change.
   - **No overfitting rule:** any proposed rule change must be validated against the *other* hand-verdicts; if it flips a previously-correct pass to fail, the change is rejected.
   - **Tool version tracking:** each rule change bumps the tool version and the set of accepted exam verdicts is re-run before the tool is trusted on new patterns.

3. **Build assignment confirmation**
   - I confirm: 4Q builds the abuse-fuzzer recipe engine (B-class recipes from ERROR_CATALOG.md), the flaky-oracle detector, and the evidence-card emitter.
   - Constraint I propose: abuse engine runs on stdlib only, no heavy model calls per pattern; token budget stays low.
   - One dependency on 6E: the evidence-card format needs to consume 6E's output-plausibility and invariant-probe results; we agree on a JSON line schema by tonight.

- `why` (sentence explaining violation)
- `confidence` (`HIGH`, `MEDIUM`, `LOW`)
- `repro_cmd`
- `seeds` (for flaky-oracle detector: list of seeds and per-seed outcomes)

Also confirm: for combined-fault injection, do we accumulate ALL violations in one card, or emit one card per violation with a `combined_with` field? I lean toward one card per violation with a `combo_id` grouping, so the report is human-readable and machine-filterable.
