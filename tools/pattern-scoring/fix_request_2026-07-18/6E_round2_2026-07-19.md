### The disagreement protocol

I thought about this as three scenarios:

**Tool says KILL, Illia says PASS (false alarm):** The tool is too aggressive. Record the override in a calibration log. If the same pattern of false alarm appears 3+ times, the tool's rule is rewritten (threshold tightened, invariant narrowed). Who moves: the tool.

**Tool says PASS, Illia says KILL (missed bug):** The tool is too weak. Illia documents the kill and the mechanism that would catch it. The tool gets a new rule or mechanism. The kill goes into the error catalog as a new class if it doesn't fit existing ones. Who moves: the tool — immediately, no three-strikes wait.

**Both say KILL, different reasons:** Both are recorded. Illia's reason is authoritative for the fix. The tool's reason is kept as a secondary signal. If the tool's reason is wrong (flagged the right file for the wrong reason), the mechanism needs adjustment.

**The calibration log:** A `CALIBRATION_LOG.md` with entries: date | pattern | tool verdict + reason | Illia verdict + reason | resolution | rule rewritten? This is the permanent record of every disagreement and its outcome.

**When does the tool's rule get rewritten?** After 3 false alarms of the same class (same invariant, same threshold, same pattern type) — OR immediately for a single missed kill. A missed kill is always a tool failure, no waiting.

## Proposals

### A1. Cut combined-fault injection, flaky-oracle, and P3 (boundary analysis) from v1 to v1.5

**Why:** 9 items for one build day by two agents is too many. These three are the lowest-value-per-build-time. The tool without them still catches all three of Illia's kills. Ship them in v1.5 after the exam passes.

### A2. Disagreement protocol: calibration log + three-strikes rewrite + immediate rewrite on missed kill

**Why:** The tool needs a path to improve without Illia having to re-litigate every disagreement. Three-strikes for false alarms prevents over-reaction to noise. Immediate rewrite for missed kills prevents the tool from staying blind to a class of bug Illia already found. The calibration log is the permanent record that prevents the same disagreement from happening twice.

### A3. Agree on the pattern entry-point convention before build day

**Why:** P1, P2, P3, and the abuse-fuzzer all need to call pattern functions generically. If every pattern has a different calling convention, the tool can't work. I propose a `run(input: dict) -> dict` wrapper convention. We need to agree on the dict schema before anyone writes code. This is a 30-minute design discussion that saves hours of integration pain.

### A4. Confirm my build assignment as-is (P1 + P2 + P3, with P3 cut to v1.5)

**Why:** The split makes sense — 4Q owns the attack generation (abuse-fuzzer, flaky-oracle, evidence cards), I own the verification mechanisms (invariant probes, output plausibility, boundary analysis). No overlap, no conflicts. If P3 is cut to v1.5, my build day is P1 + P2 only (~300 lines), which gives me time to help with integration or write the entry-point wrappers.
